# SkyJump3D static performance audit (code agent)

Scope: `index.html` (~7430 lines, three r160), main loop at `renderer.setAnimationLoop` (~L7397). Read-only; nothing run.
N-values are the six-universe counts: solids ~3000, platforms ~1800, enemies ~540, items ~4900, specials ~420, lvl children ~12k.
Real Object3D count is much higher than 12k: each enemy is a Group of ~20-40 Meshes (each with its own BoxGeometry/Material), each platform a Group of ~5 meshes. Estimate 35-45k nodes in the scene graph.
Rules honoured: no `rand()` order change, no instancing of animated enemies.

Main loop order (all per frame): playerUpdate -> updateEnemies -> updateShots -> updateItems -> updateStreet (playerShadowTick, cullTick, tryLatchRail, nearestProp, props spin...) -> updateMissions -> evolveTick/updateGrowers/dreadTick/musicTick -> updateLadderLabels/updateFx/updateGibs/updateClouds -> updateSpecials(+updatePsy) -> updateWorlds/innerVoices/updatePortals/schizoTick/updateHotbar -> updateVisuals(+updateEnv) -> setHint -> netTick/updatePeers/debugTick -> render.

## Enemy AI answer
- `walker()` L5082 and `variantAI()` L5029, `drone()` L1089 area, `ufoAI` L1119, `clientEnemy` L6245: none call `blocked()`, `heightAbove()`, `inSolid()` or loop `solids`. Walkers are clamped to their own platform rect (`e.plat` min/max), drones/ufos fly free (no ground check), so there is NO per-enemy collision scan. Per active enemy cost is `nearestPlayer`, a few `Math.hypot`, and `sfx`/`burst`/`hurt` events. Good.
- Only collision-ish loops touching enemies: `enemyContacts()` (all enemies, per substep), `castRay` (enemies + solids per shot), `updateShots` (player shots x all enemies with `Math.hypot`).

## Enemy >230 m skip: multiplayer correctness (L5153-5170)
- Rule: skip when the NEAREST of {me if `state==='play'`, alive+`seen` peers} is >230 m (boss 300 m) horizontally, or >300 m vertically. Host and guest run the same test, host with real AI, guest via `clientEnemy`.
- Host side is correct: a far peer (other universe) counts through `nearestPlayer` so enemies near any live player are simulated. Dead peers (`!p.alive`) and not-yet-`seen` peers are ignored, so enemies near a dead teammate freeze until respawn (acceptable, but cosmetic freeze mid-attack).
- Guest side: enemies in the band 120-230 m (boss 180-300) of every player are *simulated by the host* but NOT included in the 10 Hz partial snapshots (`netSnapshot(false)` radius 120 / boss 180); the guest only receives them in the 5 s full snapshot, so they appear to hop every 5 s. Harmless visually (they are in fog), but if you want strict consistency make the snapshot radius equal the sim radius (230/300) - costs bandwidth, so ask before changing.
- Skipped enemies keep their `emissive` colour if they were flashing red (`hit>0`) when they went out of range; the next in-range frame resets it. Cosmetic only.
- The second range test at L5165 duplicates the first (same predicate, same inputs): dead code; removing it is free.
- `updateEnemies` also runs during `state==='clear'` and `'dead'` (only when `net.on`); in `dead` with no alive peer `nearestPlayer` returns the corpse position (bd=1e9) so enemies keep simulating around the corpse - fine.

## Generation-time review (buildNetwork / connectFar / buildUniverseLinks), build ~14 s
- Algorithmic hot spots are NOT the cause of 14 s but are the only O(N^2) bits: `blocked()` L1592 scans all `solids` + `reserved` (up to ~3000 each) and is called 2-3x per candidate platform in `connect`, `connectFar` (L2040-2057), `walkBranch` (L3042), skyway and ladder; estimate 10-20k calls x ~1.5k solids = 15-30M compare groups (~0.1-0.4 s). Fix: bucket grid keyed by 16 m cells inserted in `addSolid` (L607) and `reserved.push`; `blocked()` becomes a boolean over 4-9 cells, result identical (no RNG), so determinism holds. PERFORMANCE_PLAN 2.1 grid can be reused for runtime `inSolid/surfaceY/castRay` too.
- `addPortal` L1473 scans all solids per portal (hundreds): same grid helps. `bounceDress` L618 does `portals.some(hypot)` per bounce platform: small. `buildNetwork` hub sorts (`hubs.slice(0,i).sort(...hypot...)`, L2227) are O(H^2 log H) with H~150: negligible.
- `connectFar` / `buildUniverseLinks`: 6 ring + 3 diagonal + up to 6 skyway + 3 retries, each `link()` tries up to 8 ranked pairs and each failing `connectFar` still returns false only AFTER its loop built platforms? No: it returns early (`L<30`, `stepMax>3.4`) before building, but a chain that places platforms and then fails `firstOk&&lastOk&&built>=4` leaves orphan platforms/enemies/items in the world (cost + clutter). Diagonals 0-3 and 2-5 (~1100 m) reject cheaply at `stepMax` per TODO. Max 64 stones x ~10 links. Cheap; fine.
- `rankedPairs` builds the full cartesian `cands(ua) x cands(ub)` (maybe 20x20) and sorts per `link` call: negligible.
- Work that runs for ALL six universes unconditionally even in solo: all 6 homes built via `activeStartHubs()` (every start hub has `active:true`): `buildHomeBase` x6, 3 props x6, arsenal pickups x6 (5 weapons each), lore terminal x6, guide NPC x6; `buildBranches` seeds from `platforms.filter(near any home)` .slice(0,8) per all homes (walkBranch x2 each); `spawnStreetRiders`. This is required for determinism and co-op parity, but in solo mode the 5 foreign universes are 1100+ m of unused geometry on first load. Safe lever (ask): build foreign universes' enemies/items lazily (see #4/#5) - generate only the cheap data (keeping every `rand()` call in place) and defer meshes.
- Each `buildLevel` is re-run by `applyNetSlot` (joining a room) and by a mismatching `state` message - a second full 14 s build for every guest. Cache/skip when `level` and `seed` already match (`applyNetSlot` only needs to move `pos`/`start`/mission slot because all six towers always exist; the only slot-dependent things are `mySlot` missions/guide and spawn - verify `generateMissions` can be re-run alone).
- Leak: `retroMaterials` (Set, L246) and `retroTextures` are never cleared in `buildLevel`; every rebuild keeps ~15-20k dead materials alive (and `lvl.traverse` disposes geometries only, never materials), so memory doubles per rebuild and a preset switch iterates all stale entries. Fix: in `buildLevel` dispose materials in the old `lvl` and `retroMaterials.delete` them.
- The monkey-patched `Object3D.add` (L287) traverses the added subtree each add; building a platform adds parts to `grp` then `grp` to `lvl` (every node traversed twice), enemies same. Set `userData.skipRetrofit` or no-op `retroMaterial` fast path in MODERN (it already returns early after `Set.add`; the `Set.add` + `userData ||= {}` alone costs ~tens of thousands of calls).
